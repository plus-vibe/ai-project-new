## Что обсудим на лекции

Лекция охватывает четыре этапа: индекс (создание единой структуры для поиска), поиск (стратегия под термины, сложность вопроса), ответ (собрание доказательств и связь с источниками), проверка (различие ошибки поиска и ошибки генерации). Результат — обоснованный выбор архитектуры для задачи. Система состоит из четырёх компонентов.

## RAG: от источников к ответу

Архитектура RAG включает подготовку базы знаний (источники → фрагменты → представления → индекс) и генерацию ответа (вопрос → поиск → отбор → промпт → LLM). Ключевая идея — найти релевантные данные, затем дать модель контекст. Лексический поиск не требует эмбеддингов; reranking — опциональный этап. Ответ включает ссылки на источники.

Источник: [b004](#source-b004)

## Naive, Advanced и Modular RAG

Таблица классифицирует три подхода к RAG: Naive RAG — один поиск top-k и один вызов генератора; Advanced RAG — улучшение индекса, запроса, отбора и контекста; Modular RAG — комбинирование модулей, маршрутов и циклов. Подходы различаются по сложности и гибкости архитектуры. Границы классификации условны.

Источник: [b005](#source-b005)

## Где ломается базовый RAG

Базовый RAG имеет ограничения: 1) Нет в индексе — парсер пропустил таблицу или документ устарел. 2) Не нашли — вопрос и нужный фрагмент используют разные формулировки. 3) Потеря при отборе — важное исключение не попало в итоговый контекст. 4) Неверно ответили — модель перепутала источники или добавила неподтверждённое. Каждый тип ошибки требует своей проверки.

## Подготовка корпуса

Процесс подготовки корпуса включает: извлечение текста, таблиц, OCR и логической структуры; нормализацию (удаление повторов, колонтитулов, кодировок, переносов строк); присвоение метаданных (документ, версия, страница, раздел, координаты); контроль сопоставления извлеченного текста с оригиналом. Важно сохранить структуру, убрать технический шум и не потерять данные.

Источник: [b008](#source-b008)

## Извлечение данных для RAG

Таблицы в PDF требуют pdfplumber и Camelot для извлечения ячеек и структуры. Для DOCX — docx2txt (текст+изображения). Для Word — python-docx и Mammoth (абзацы, стили, таблицы). Unstructured — для разных форматов (заголовки, списки, метаданные). Docling — для сложной структуры (OCR, порядок чтения). Старые .doc — через LibreOffice. Сканы внутри документов — OCR через выбранный движок. Для RAG сохраняют: текст, заголовки, таблицы, порядок чтения, источник.

Источник: [b009](#source-b009)

## Что есть из новых подходов? Docling*

Docling — система для обработки документов. Представляет два потока: PDF Pipeline (Parse PDF pages → OCR → Layout Analysis → Table Structure → Assemble Document) и Simple Pipeline (Parse Markup Format → Assemble Document). Результат — Docling Document, который можно экспортировать в JSON, Markdown, HTML и используется для Chunking для RAG. Ссылка на arXiv: https://arxiv.org/html/2501.1788?v1. Условие: «Ни один парсер не способен учесть все нюансы...» (habr.com.ru/articles/893356/).

Источник: [b010](#source-b010)

## OCR для RAG: Русский язык и структура

Таблица инструментов OCR: Tesseract + pytesseract, OCRmyPDF, EasyOCR, PaddleOCR, RapidOCR. Указана поддержка русского языка и особенности. Предварительные шаги: проверка текстового слоя, исправление поворотов, выбор языков. После распознавания: восстановление структуры, проверка данных, сохранение координат. Ключевое: распознать слова ≠ восстановить структуру. Важно: нейросетевые решения также поддерживают русский язык.

## Предобработка и чанкинг: готовые инструменты

Семантический чанкинг в RAG — LlamaIndex. Пример: измерение сходства эмбеддингов для границы. Настройка под данные: очистка колонтитулов, размер чанков, метаданные. Алгоритмы в библиотеках, качество проверяется на документах.

## Размер chunk и overlap

Малый chunk: точный поиск, но условия могут быть за границей. Большой chunk: больше контекста, но вектор может смешивать темы. Overlap: снижает риск потери связей, увеличивает дубли. Эксперимент: сравнение вариантов на одинаковой разметке доказательств. Универсального оптимального размера нет.

Источник: [b013](#source-b013)

## Parent-child retrieval

Индекс содержит малые дочерние фрагменты с parent_id. При поиске ищется точный дочерний фрагмент. В контексте возвращается более крупный родительский раздел. Ограничение: несколько совпадений могут возвращать один и тот же большой раздел. Единица поиска и единица контекста могут различаться.

Источник: [b014](#source-b014)

## Sentence-window retrieval

Индексируются отдельные предложения или короткие сегменты. Расширение — добавление соседних предложений из исходного документа. Пример: «Он утверждает заявку» + предложение с именем роли. Ограничение: окно не должно пересекать чужой раздел или документ. Поиск точный, ответ — локальный контекст.

Источник: [b015](#source-b015)

## Contextual Retrieval

Проблема: фрагменты без контекста (например, «Выручка выросла на 8%») не содержат компании и периода. Решение: LLM создаёт пояснение, которое добавляется к чанку для embeddings и BM25. Индексация: сохраняется оригинальный чанк отдельно от пояснения. Цель: дополнительный контекст помогает понять фрагмент при поиске.

Источник: [b016](#source-b016)

## Late Chunking

Late Chunking — метод, при котором длинный текст кодируется до pooling, а затем вычисляются средние значения token embeddings только в границах фрагмента. Требование: embedding-модель должна поддерживать нужную длину входа. Представление фрагмента учитывает окружающий текст. В отличие от обычной схемы, где каждый чанк кодируется отдельно, здесь кодирование происходит на уровне всего фрагмента.

Источник: [b017](#source-b017)

## Метаданные и доступ

Метаданные используются для поиска (организация, тип, дата, язык, версия), ссылок (название, раздел, страница, идентификатор), прав (пользователь, группа, tenant, набор документов) и обновлений (хеш содержимого, связь с исходным документом). Метаданные влияют на качество и корректность доступа.

Источник: [b018](#source-b018)

## Множественные представления документа

Метод Multi-Representation Retrieval использует несколько представлений: оригинал (точный текст для подтверждения), резюме (краткое представление раздела), вопросы (синтетические, на которые отвечает chunk), связь (каждое представление указывает на исходный фрагмент). Поиск ведется по удобному представлению, подтверждаемому оригиналом. Важно: каждое представление связано с исходным фрагментом.

Источник: [b019](#source-b019)

## Жизненный цикл индекса

Жизненный цикл индекса включает: изменение — перестройка фрагментов изменённого документа; удаление — удаление связанных представлений и записей из кэша; смена модели — пересчёт совместимого индекса; фиксация версии — заморозка корпуса, парсера и конфигурации для воспроизводимости. Актуальность базы требует отдельного процесса.

Источник: [b020](#source-b020)

## 03. Поиск и отбор

Блок посвящен типам retrieval: лексический, семантический и гибридный. Упоминается термин "retrieval" как ключевая концепция раздела.

Источник: [b021](#source-b021)

## Лексический поиск: BM25

BM25 — алгоритм лексического поиска, основанный на совпадении терминов, с коррекцией по редкости, частоте и длине документа. Использует оценку TF-IDF, учитывая насыщение термина и корректируя влияние длины. Примеры: код ошибки, название продукта, идентификатор события. Основан на работе Robertson & Zaragoza, 2009. Эффективен для точных терминов, но не адаптируется к переформулировкам.

Источник: [b022](#source-b022)

## Dense retrieval

Encoder преобразует запрос и фрагмент в векторы. Сходство оценивается по dot product или cosine. Сильная сторона — поиск близкого смысла при разных формулировках. Риск — похожие темы могут быть разными фактами. Семантическое сходство полезно, но не доказывает релевантность. Заметка: полезно при переформулировках; точный поиск работает хуже.

Источник: [b023](#source-b023)

## Обучаемый sparse retrieval: SPLADE

SPLADE — обучаемый sparse retrieval, использующий разреженные взвешенные термины словаря. Модель может расширять текст, а разреженные признаки подходят для inverted index. Качество сопоставления зависит от разреженности и стоимости. Система может быть обучаемой и семантически обогащённой.

Источник: [b024](#source-b024)

## Late interaction: ColBERT

ColBERT использует несколько векторов документа вместо одного. Каждый токен запроса ищет лучшие совпадения в документе. Оценка формируется как сумма лучших сходств. Хранение и поиск сложнее, чем для одного вектора. Более подробное сопоставление сохраняет локальные сигналы. Механизм Maxim используется для сравнения токенов.

Источник: [b025](#source-b025)

## Гибридный поиск

Таблица содержит три канала: BM25 (термины и редкие названия, пример: «Event ID 4625»), Dense (смысл и перефразирование, пример: «Почему не получается войти?»), Точный retriever (ID и строки со спецсимволами, пример: «rule_login_failed»). Объединение каналов расширяет набор кандидатов. На практике используется гибридный поиск.

Источник: [b026](#source-b026)

## Объединение рангов: RRF

Формула: score(d) = Σ 1 / (c + rank_i(d)). Вход — позиции документа в списках результатов. Отсутствие — вклад 0, если документ не попал в список. Параметр c — сглаживает вклад первых позиций, выбирается экспериментально. Ранги можно объединять без сравнения score.

Источник: [b027](#source-b027)

## Приближённый поиск и фильтры

ANN ускоряет поиск соседей, допускает пропуск кандидатов. Параметры — управление компромиссом recall, latency и памяти. Фильтры ограничивают поиск метаданными и правами доступа. Проверка — сравнение выборки ANN с точным поиском по набору. Высокое качество embeddings не гарантирует recall индекса.

Источник: [b028](#source-b028)

## Reranking

Быстрый retriever собирает широкий набор кандидатов. Reranker оценивает пару «вопрос, фрагмент». Выбираем меньшее число фрагментов по новой оценке. Reranker не возвращает документ, отсутствующий среди кандидатов. Высокий recall и точный отбор решают разные задачи. Заметка: требуется точный выбор документов; cross-encoder дорог.

Источник: [b029](#source-b029)

## Разнообразие результатов: MMR

MMR предпочтет фрагменты, близкие к запросу. Штрафует сходство с уже выбранными фрагментами. Параметр λ управляет балансом между релевантностью и разнообразием. Слишком сильное разнообразие добавляет слабые доказательства. MMR уменьшает повторение одного и того же. Notes: не добавляет лишние вещи; не включает похожие документы.

Источник: [b030](#source-b030)

## Топ-k и пороги

Топ-k — фиксированное число результатов, может включать нерелевантные. Порог — позволяет вернуть мало результатов или ничего. Калибровка: score зависит от модели, корпуса и способа вычисления. Отказ: недостаток доказательств должен влиять на поведение ответа. Cosine score ≠ вероятность правильного ответа. В notes: если нет релевантной информации, лучше использовать этот способ; если модель глупая — тоже лучше.

Источник: [b031](#source-b031)
